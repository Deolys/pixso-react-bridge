# Pixso → React: локальный MCP для GigaCode

Node.js MCP-сервер и CLI: сохраняет полный проверяемый снимок макета Pixso, распределяет анализ между процессами GigaCode, создаёт React + TypeScript + обычные CSS-классы и проверяет каждый экран в локальном браузере. Плагин GigaCode — необязательная оболочка из skill и инструкций; основная логика выполняется локально в Node.

**Важная граница:** пакет реализован и проверяется тестами и независимым визуальным демо. Корпоративные Pixso и GigaCode в среде разработки недоступны; проверка на их реальной сборке нужна при подключении. Ни отсутствие данных, ни успешное завершение ИИ-процесса не считаются завершённым переносом.

## Быстрый запуск

Нужны Node.js 22.12+ (рекомендуется 24 LTS), установленный и авторизованный GigaCode CLI, React-проект с его зависимостями и Pixso с включённым MCP. Для браузерной проверки достаточно локального Chrome/Edge либо Chromium Playwright.

ZIP поставки содержит исходники, готовую сборку и `package-lock.json`; команды ниже выполняются в распакованной папке. Для установки готового npm-архива используйте `npm install -g C:/downloads/pixso-react-bridge-1.2.0.tgz`, затем `pixso-react` вместо `node dist/cli.js`. Сборка npm-архива уже выполнена, `npm ci` для него не нужен. Проверки поставки и снимки: [отчёт](docs/verification.md).

```powershell
# В директории этого пакета
npm ci
npm run build
npm test

# Путь к существующему React-проекту
node dist/cli.js init --project C:/work/my-react-app
node dist/cli.js install --config C:/work/my-react-app/pixso-react.config.json
```

`init` предлагает `<проект>/.pixso-artifacts` через созданный конфиг. Другой каталог задаётся `--artifacts D:/design-artifacts` либо в `artifactsDir`. `install` аккуратно добавляет сервер в `.gigacode/settings.json` и skill в `.gigacode/skills/pixso-react`, сохраняя существующие настройки. Перезапустите GigaCode в целевом проекте.

В `pixso-react.config.json` укажите `pixso.fileKey` и, если нужна только часть файла, `pixso.nodeIds`. Без `nodeIds` захватывается весь документ. Локальный endpoint по умолчанию — `http://127.0.0.1:3667/mcp`. [Другие подключения и ограничения](docs/pixso.md).

Для установленного Chrome без загрузки Chromium задайте `validation.browserChannel: "chrome"` (Edge — `"msedge"`). Также поддерживается `validation.executablePath` для корпоративного браузера. Playwright открывает только локальный результат, вход в Pixso через браузер ему не нужен.

Если GigaCode — Windows `.cmd`-обёртка, задайте `gigacode.command: "node"`, а первым аргументом — абсолютный путь к JS entrypoint установленного CLI. Подробности, реальные формы запуска и автоматическое обнаружение флагов — в [руководстве GigaCode](docs/gigacode.md). Команды никогда не собираются в shell-строку.

После настройки можно сказать GigaCode:

> Используй pixso-react MCP. Проверь подключение, захвати выбранный макет, затем запусти transfer с четырьмя работниками. Используй компоненты и CSS-паттерны этого проекта. Следи за job_status и исправлениями до общей проверки всех экранов. Если проверка не прошла, сообщи конкретные несоответствия и путь к отчёту.

## Такой же путь через CLI

```powershell
node dist/cli.js inspect --config C:/work/my-react-app/pixso-react.config.json
node dist/cli.js capture --config C:/work/my-react-app/pixso-react.config.json
# capture вернёт полный путь snapshot
node dist/cli.js transfer --snapshot "D:/design-artifacts/designs/.../versions/..." --config C:/work/my-react-app/pixso-react.config.json --iterations 2
```

`transfer` выполняет анализ → реализацию → перенос файлов → TypeScript → дополнительные команды проекта → визуальную проверку всех экранов. При несовпадениях следующий ограниченный проход получает отчёт для исправления. `--iterations` допускает 1–5 проходов. Каждая попытка и версия сохраняется. При ошибках CLI возвращает ненулевой exit code, `complete` остаётся `false`.

По умолчанию код появляется в `src/pixso-generated`, каждый экран в своей папке, общий `index.ts` экспортирует `Screen1`, `Screen2` и далее. В `applied.json` есть полный список файлов. Подключение экранов к бизнес-маршрутам проекта остаётся явным шагом: без знания маршрутизатора менять существующие страницы автоматически нельзя. Обязательная проверка использует временный локальный Vite preview именно установленных файлов. `validation.url`, например `http://127.0.0.1:5173/design-preview?screen={screenId}`, добавляет проверку интеграции в проекте, но не заменяет обязательную. Нужные моки, props и провайдеры подключаются через `validation.setupFile` с экспортом `preparePixsoPreview({screenId})`.

`generation.cssFiles` — относительные пути к общим CSS проекта; они также подключаются в preview. `generation.componentFiles` ограничивает список компонентов для анализа. При пустых массивах исследуются существующие `.css`/`.tsx`/`.jsx` файлы, до 400 найденных файлов; ограничение отражается в profile. Агенты читают реальные исходники и API подходящих компонентов. Новая UI-библиотека по умолчанию не добавляется. Макет сам по себе не задаёт серверную логику, API или отсутствующие в нём состояния приложения.

## Часть экрана или микрофронтенд

Для отдельной области задайте корневой Pixso ID в `--nodes`; несколько IDs разделяются запятыми. В перенос попадут выбранные узлы и все их потомки. Родители сохраняются как контекст, а соседние части хост-приложения не становятся задачами вёрстки.

```powershell
node dist/cli.js capture --nodes "12:34" --scope-name "Карточка заказа" --config C:/work/my-react-app/pixso-react.config.json
# Новый scoped snapshot из уже сохранённой версии
node dist/cli.js scope --snapshot "D:/design-artifacts/designs/.../versions/..." --nodes "12:34" --scope-name "Карточка заказа" --config C:/work/my-react-app/pixso-react.config.json
```

Для `scope` нужен независимый PNG именно выбранного корня в исходной версии. Если там есть только снимок целого экрана, повторите `capture --nodes` через Pixso либо импортируйте точный экспорт выбранной области. Обрезка снимка хоста не считается таким эталоном. [Области переноса и версии](docs/scopes-and-versions.md).

## Данные и моки проекта

С версии 1.2 анализ различает подписи интерфейса и бизнес-значения из примера макета. Имена клиентов, суммы, даты, счётчики и строки данных поступают через реальные props/hooks/context. Примерные значения размещаются в существующих моках, фикстурах или фабриках проекта. Поддерживаются обнаружение MSW, Mirage, json-server, Storybook и собственного механизма проекта; новую библиотеку плагин автоматически не добавляет.

Укажите `generation.data.mockFiles`, при необходимости `generation.data.instructions` и `validation.setupFile`. Последний экспортирует асинхронный `preparePixsoPreview({screenId})`, возвращающий `{props?, Provider?}`; он подготавливает данные только для preview. `generation.data.setupFile` указывает существующий bootstrap моков для анализа и не запускается автоматически: при необходимости его вызывает preview setup. В рабочие View моки не импортируются.

Если подходящего сценария, API или настройки preview нет, результат — `blocked-project-data` до реализации и apply. `data-plan.json` и **`data-gaps.md`** содержат причины, экран/ID, нужные доработки и задание для ИИ. После добавления сценария штатными средствами проекта выполните новый анализ. [Настройка и пример](docs/project-data.md), [полный пример конфига](examples/project-data.config.json).

## Pixel perfect и недостающие компоненты

По умолчанию `validation.mode: "pixel-perfect"`: допускается **0 отличающихся RGBA-пикселей**, без игнорирования сглаживания или масштабирования эталона. Для каждого экрана обязательны PNG из исходного дизайна, стабильное изображение, DOM/тексты/геометрия, проверка шрифтов и успешная компиляция. Только общий отчёт с `pixelPerfect: true` и `complete: true` подтверждает результат на захваченных размерах экрана и в указанном браузере. Наличие MCP и успешный ответ модели сами по себе точности не гарантируют.

Укажите выбранную систему через `generation.designSystem: {"name":"Корпоративная UI","packageName":"@company/ui"}` и добавьте её реальные исходники/обёртки в `componentFiles`, CSS — в `cssFiles`. `packageName` необязателен для локальной библиотеки. Каждый узел требует решения `native`, `reuse`, `adapt`, `create` или `unknown`, а повторное использование — доказательств из настоящих исходников/API. Неполная инвентаризация также блокирует приёмку.

Если компонент отсутствует, не поддерживает нужный вариант или требует адаптации, результат — `blocked-design-system` **до реализации и apply**. В папке запуска появляются `component-plan.json` и **`component-gaps.md`**: экран/ID, что требуется, что есть в библиотеке, необходимые изменения и готовое задание для ИИ. GigaCode обязан сообщить эти проблемы пользователю. После добавления/адаптации компонентов выполняется новый анализ и transfer; ближайшая похожая замена не допускается.

`validation.mode: "tolerant"` доступен только для диагностики: даже нулевая перцептивная разница не даёт `pixelPerfect` или `complete`. Старые конфиги без `mode` используют строгий режим. Старые снимки без SHA эталонных PNG нужно захватить или импортировать новой версией. Подробные критерии и ограничения: [pixel perfect](docs/pixel-perfect.md).

## Полнота без обрезания

1. Node напрямую обращается к Pixso MCP и сохраняет необработанные ответы на диск. Дерево не пересылается целиком через LLM.
2. Независимый список узлов сравнивается с сериализованными свойствами. Сохраняются геометрия, layout, padding/gap, fills/strokes, текст и диапазоны стилей, переменные, компоненты, изображения, векторы и неизвестные читаемые свойства.
3. Даже один очень большой узел, стиль или изображение читается по частям с длиной, смещением и отпечатком. Проверяются ссылки, отношения родитель/дети, порядок, количество и стабильность данных до/после захвата.
4. Каждый исходный JSON сохранён полностью. Для ИИ есть ограниченные UTF-8 части, индекс IDs и отдельные задания по экранам/крупным виджетам. Делятся и анализ, и реализация; координатор собирает виджеты по стабильным экспортам и сверяет покрытие всех IDs. Размер заданий ограничен числом узлов и объёмом данных. Огромные одиночные значения сохраняются и обрабатываются программно, без вставки целиком в контекст модели. Части можно без потерь собрать обратно.
5. `complete` у снимка означает полноту доступного API в выбранной области. `complete` у итогового transfer требует успешной общей проверки кода и **всех** экранов. Это разные проверки.

Импорт проверяет граф и количество узлов, не разрешает ассетам ссылаться вне папки экспорта. Урезанный DSL старого сервера можно исследовать, но нельзя объявить полным снимком.

## Артефакты и обновления

```text
.pixso-artifacts/
  captures/<capture-id>/                 исходные MCP ответы и диагностика
  designs/<file-key>/versions/<time-id>/  новая папка при каждом захвате
    manifest.json                       SHA-256, источник, экраны, количество
    capture.json                        полная каноническая модель
    node-index.json                     ID → файл/части/хеш
    nodes/                              полный JSON каждого узла
    chunks/                             части UTF-8 без потери символов
    pages/<page>/screens/<screen>/       индекс экрана
      CHANGELOG.md                      необязательно: дата и краткие изменения
      widgets/                          непересекающиеся группы анализа
    assets/                             оригинальные изображения и SVG
    references/                         независимые PNG Pixso
    raw/                                MCP ответы и разрешённые ссылки
    runs/                               планы, попытки, код, логи, проверки
  jobs/<job-id>/                        состояние фоновых заданий
  workspaces/<task-hash>/<attempt>/     короткие рабочие пути агентов для Windows
```

Новый макет — новый `capture`, затем `diff --before OLD --after NEW` показывает добавленные, удалённые и изменённые IDs. Предыдущая версия не перезаписывается. Повторный `run --run DIR --resume` переиспользует только задания с теми же входными данными, командой и неповреждёнными выходными файлами. Локальные изменения уже перенесённых файлов защищаются ledger: при конфликте автоматическая перезапись прекращается. Удалённые в новом дизайне файлы автоматически не удаляются; список `diff.removed` нужен для явной уборки и проверки ссылок.

Короткий журнал выключен по умолчанию: `versioning.screenChangelog: false`. Включите его в конфиге, чтобы каждая новая версия содержала ровно один `CHANGELOG.md` на экран, либо передайте `--change-note "Обновлены поля заказа"` для одной операции `capture`, `import` или `scope`. Сравниваются тот же файл, набор корней выборки и screen ID; базовую версию можно явно задать `--previous-snapshot OLD`. Запись содержит дату, предыдущую версию и краткие категории изменений; старые версии не дописываются.

## MCP-инструменты

| Инструмент | Назначение |
|---|---|
| `pixso_status`, `pixso_inspect` | конфигурация и реальные возможности Pixso |
| `pixso_start_job`, `pixso_job_status` | фоновый `capture`, `run`, `transfer`, `verify` |
| `pixso_import`, `pixso_snapshot` | импорт и проверка целостности снимка |
| `pixso_scope` | новая версия выбранной части сохранённого макета |
| `pixso_plan`, `pixso_baseline` | план работ и исходная React-вёрстка |
| `pixso_apply`, `pixso_accept` | перенос кода и общая проверка |
| `pixso_diff` | различия версий |
| `pixso_read_artifact` | точное чтение текста с `offset`/`nextOffset` |

`pixso_read_artifact` возвращает максимум 24 000 символов, явную длину и `nextOffset`; нужно читать до `null`. Картинки открываются по локальному пути. Длительные работы запускаются фоном, MCP-ответ содержит job ID, а не мегабайты логов.

Для фонового `capture` инструмент `pixso_start_job` принимает `nodeIds`, `scopeName`, `changeNote`, `previousSnapshot`; `pixso_scope` принимает `snapshot`, `nodeIds` и те же необязательные поля. Проверяйте фактическую схему MCP установленной версии перед вызовом.

## Проверка и пределы

`npm test` проверяет перенос больших данных и Unicode, граф/ссылки/ассеты, разные версии, повреждение артефактов, swarm concurrency/retry/resume/timeout, literal arguments, React/CSS и PNG diff. `npm run demo` строит реальный React-экран, сравнивает его с независимо написанным эталоном и выполняет отрицательный тест с неверным цветом. Демо сохраняет результаты в `output/demo` и использует локальный Chrome, если Chromium Playwright не установлен.

Статическая геометрия из исходного генератора — отправная точка. Необычные маски, blend/effects, шрифты, сложные gradients и responsive-правила могут потребовать правки GigaCode; они не замалчиваются. Проверка выполняется на размерах захваченного экрана. Если нужны отдельные мобильные состояния, их надо включить в область захвата как экраны; неизвестные брейкпоинты не выдумываются. Строгая геометрическая проверка допускает 0.01 px для округления DOM, но растровое сравнение по-прежнему требует нулевой разницы.

Шрифты должны быть доступны локальному браузеру либо подключены CSS проекта. Скрытые узлы сохраняются. Тексты и элементы интерфейса не подменяются картинкой всего экрана; SVG разрешён для иллюстраций. Ошибка сборки, отсутствующий узел/PNG/ассет или превышение допуска означает неготовый перенос. Результат агентов — исполняемый код: они получают только необходимые локальные данные, однако изоляция рабочих папок не является системной sandbox.

Токены Pixso задаются через `pixso.headersEnv`, например `{ "Authorization": "PIXSO_AUTHORIZATION" }`; значение переменной содержит полный заголовок, включая `Bearer`, если он требуется. Сырые артефакты содержат дизайн и тексты: храните их в допустимой корпоративной директории и добавьте `.pixso-artifacts/` в `.gitignore` проекта.

Первичные источники и подтверждённые контракты перечислены в [Pixso](docs/pixso.md) и [GigaCode](docs/gigacode.md). Решение не обещает универсальную точность без проверки на реальном файле: оно даёт воспроизводимый процесс, сохранённые данные и измеримый критерий готовности.
