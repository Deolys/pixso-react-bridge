# GigaCode CLI: запуск роя

Основной runtime — локальный Node.js MCP-сервер и CLI `pixso-react`. GigaCode подключает MCP и запускает работу с локальными версиями макета. Optional `gigacode-extension.json`, skill и именованные агенты содержат инструкции; они не заменяют захват данных, очередь заданий и проверки runtime.

Речь о **GigaCode от GitVerse/Сбера**. Одноименные проекты Rivet, Kolega и пакеты `gigacode` других авторов несовместимы. Установить и авторизовать корпоративный GigaCode нужно по инструкции вашей организации. На машине разработки этого пакета GigaCode не найден; реальный вызов корпоративной модели не проверялся. Проверены процессы-имитаторы и полный локальный контур там, где это отдельно отражено в отчёте проекта.

## Подключение runtime и работа через MCP

После установки/сборки пакета выполните из каталога проекта:

```text
pixso-react init --project .
pixso-react install --config pixso-react.config.json
```

`init` создаёт конфигурацию, если её ещё нет. Настройте в ней подключение к вашему Pixso MCP, исполняемый GigaCode, CSS/компоненты и проверки проекта. `install` добавляет локальный stdio MCP `pixso-react` в `.gigacode/settings.json` и skill в проект; конфликтующие существующие записи сохраняются. Команда не устанавливает сам GigaCode. Перезапустите GigaCode и вызовите `pixso_status`.

| MCP tool | Назначение |
| --- | --- |
| `pixso_status` | Проверить конфигурацию и пути |
| `pixso_inspect` | Получить реальные tools/schemas подключённого Pixso MCP |
| `pixso_start_job` | Запустить `capture`, `run`, `transfer` или `verify` в фоне |
| `pixso_job_status` | Получить компактное состояние фоновой работы |
| `pixso_import` | Импортировать полный локальный `capture.json` |
| `pixso_scope` | Создать новую версию выбранного фрагмента с контекстом родителей |
| `pixso_snapshot` | Проверить целостность версии и получить список экранов |
| `pixso_plan` | Подготовить профиль проекта и задания анализа |
| `pixso_baseline` | Сгенерировать исходную React/TS/CSS версию, требующую адаптации |
| `pixso_apply` | Перенести staged-результат с защитой пользовательских правок |
| `pixso_accept` | Сводная проверка TypeScript, настроенных команд проекта и всех экранов |
| `pixso_diff` | Сравнить две версии по стабильным node IDs |
| `pixso_read_artifact` | Прочитать точный диапазон текста; продолжать по `nextOffset` |

Автоматическая последовательность: `pixso_inspect` → capture/import → `pixso_snapshot` → `pixso_start_job(action="transfer", snapshot=..., iterations=2)` → дождаться результата и изучить acceptance report. Transfer выполняет анализ, генерацию, apply, проверки экранов и ограниченные попытки исправления. Для ручного управления этапами: `pixso_start_job(action="run", snapshot=...)` → `pixso_apply` → `pixso_start_job(action="verify", snapshot=..., screenId=..., url=...)` для каждого экрана. Подключение к маршрутам и бизнес-логике исходного проекта требует его реальных правил; отдельный preview экрана не доказывает интеграцию этих правил. Сохраняйте `jobId`, `runDir` и пути отчётов. Для исправлений передайте отчёт как `repairReport` в новый `run`; для продолжения прерванного запуска используйте прежний `runDir` и `resume: true`.

Те же операции доступны через CLI: `pixso-react help` показывает параметры `capture`, `import`, `scope`, `snapshot`, `plan`, `generate`, `run`, `transfer`, `apply`, `accept`, `verify`, `diff`, `start`, `status`. Локальные снимки и длинные результаты читаются из артефактов, а не возвращаются одним огромным сообщением MCP.

Для частичного экрана или микрофронтенда передавайте `nodeIds` в фоновый capture (CLI `--nodes "12:34,56:78"`) и необязательный `scopeName`. В реализации участвуют корни и потомки; предки остаются контекстом. `pixso_scope` получает исходный `snapshot`, `nodeIds` и создаёт новую версию без изменения старой. Для выбранных корней обязательны независимые PNG; crop хоста не принимается. Параметры `changeNote` и `previousSnapshot` доступны capture/import/scope. `versioning.screenChangelog` по умолчанию `false`; включённая опция или явная заметка создаёт ровно один короткий датированный `CHANGELOG.md` на экран новой версии. [Подробности областей и версий](scopes-and-versions.md).

## Подтвержденные точки интеграции

Проверено по первичным источникам 16 октября 2026:

- [Быстрый старт GitVerse](https://gitverse.ru/docs/ai/ai-assistant-gigacode/getting-started-with-gigacode/quick-start): команда `gigacode --version`; доступ CLI для организации/B2B/on-premise, установка через GitVerse.
- [MCP](https://gitverse.ru/docs/ai/ai-assistant-gigacode/gigacode-cli/mcp): серверы в `mcpServers` файла `.gigacode/settings.json` либо `~/.gigacode/settings.json`. Для локального stdio используются `command`, `args`, при необходимости `cwd`, `env`. Для Streamable HTTP — `httpUrl`, для SSE — `url`. Неинтерактивный запуск ожидает discovery MCP до первого задания.
- [Skills](https://gitverse.ru/docs/ai/ai-assistant-gigacode/gigacode-cli/skills): проектный каталог `.gigacode/skills/<name>/SKILL.md`, пользовательский — `~/.gigacode/skills/`; ручной вызов `/skills <name>`.
- [Субагенты](https://gitverse.ru/docs/ai/ai-assistant-gigacode/gigacode-cli/subagents): `.gigacode/agents/*.md`, Markdown с YAML frontmatter. Именованный агент получает отдельный контекст; `fork` документирован для интерактивного режима и общей рабочей директории. Поэтому этот runtime управляет отдельными процессами с ограниченной параллельностью и отдельными каталогами результатов.
- [Команды](https://gitverse.ru/docs/ai/ai-assistant-gigacode/gigacode-cli/commands): проектные команды лежат в `.gigacode/commands/`; GigaCode поддерживает обычные `@`-ссылки на файлы. Нельзя подставлять весь макет одной ссылкой на каталог: это может снова переполнить контекст.
- [Первичный пример расширения команды Сбер ID](https://gitverse.ru/sber_id/frontend_sdd/content/master/gigacode-extension.json): manifest `gigacode-extension.json` с полями `name`, `version`, `description`, `skills`, `commands`, `contextFileName`. Поле `agents` описано в документации субагентов.

Публичный официальный reference флагов headless-запуска не найден. Пакет **не предполагает**, что `-p` или `--prompt` есть во всех корпоративных сборках. При `gigacode.args: []` он запускает установленный executable с `--help`, сохраняет вывод и выбирает только объявленный `--prompt-file`, `--prompt` или подходящий `-p`. Если выбор невозможен, запуск завершится понятной ошибкой. Флаг `--approval-mode auto-edit` добавляется автоматически только если оба значения есть в help.

## Конфигурация процессов

Пример секции `gigacode`:

```json
{
  "command": "gigacode",
  "args": [],
  "concurrency": 4,
  "timeoutMs": 900000,
  "retries": 1
}
```

`command` — executable, `args` — массив отдельных аргументов, а не shell-строка. При явном `args` требуется `{promptFile}` или `{prompt}`. Используйте точные флаги из `gigacode --help` вашей версии. Например, **только если установленный CLI объявляет эти флаги**:

```json
{
  "command": "C:/Tools/GigaCode/gigacode.exe",
  "args": ["--approval-mode", "auto-edit", "--prompt", "{prompt}"],
  "concurrency": 4,
  "timeoutMs": 900000,
  "retries": 1
}
```

| Placeholder | Значение |
| --- | --- |
| `{promptFile}` | Абсолютный путь к UTF-8 файлу с полным заданием |
| `{prompt}` | Короткая инструкция прочитать этот файл и выполнить задание |
| `{workspace}` | Отдельный cwd текущей попытки |
| `{outputDir}` | Каталог для всех результатов текущей попытки |
| `{taskId}` | Идентификатор экрана/виджета в очереди |
| `{projectRoot}` | Исходный React-проект для чтения паттернов и компонентов |

Большие промпты и дизайн не помещаются в argv: GigaCode читает файл задания и затем перечисленные части артефактов. Сам runner не обрезает stdout/stderr и не загружает весь вывод модели в память.

На Windows `.cmd`/`.bat` нельзя безопасно запускать через `spawn` без shell. Укажите native `.exe` либо `command: "node"` и абсолютный путь к JavaScript entrypoint корпоративного CLI первым элементом `args`. Дальше следуют поддерживаемые headless-флаги и placeholder. Runtime не использует `cmd /c`, конкатенацию команд или `shell: true`.

Окружение и авторизация наследуются. `gigacode.env` позволяет добавить переменные процесса. Не размещайте токены в argv: аргументы записываются в `invocation.json`. stdout/stderr — полный исходный вывод CLI; корпоративные правила доступа к артефактам применяются и к этим журналам. Runner не читает и не переносит файлы авторизации автоматически.

Команды `validation.commands` запускаются последовательно в `projectRoot` тем же способом без shell и с таймаутом `gigacode.timeoutMs`. У каждой сохраняются exit status, длительность и полные stdout/stderr. Пустой список возвращает `not-configured`, а не `passed`: отсутствие команды сборки проекта не является доказательством успешной сборки.

## Каталоги, возобновление и проверка

Рекомендуемая директория артефактов — `<project>/.pixso-artifacts`, её можно заменить в `pixso-react.config.json`. Версии макета и запуски разделены. У каждой параллельной задачи есть собственная последовательность попыток:

```text
<run>/analysis/ или implementation/
  .swarm.lock                    # только на время работы
  gigacode-help.txt               # при автоматическом выборе флагов
  swarm-result.json
  tasks/<task-id>/
    task.json
    result.json
    attempt-0001/
      prompt.md
      invocation.json
      stdout.log
      stderr.log
      workspace/output/...
```

В основном pipeline рабочие cwd и output размещаются отдельно в `<artifactsDir>/workspaces/<run-task-hash>/<attempt-id>/`, чтобы Windows запускал процесс даже при глубоко вложенной версии макета. В каталоге попытки остаются полные логи, копия prompt и `workspace.json` с точными путями; сам prompt для CLI также лежит в коротком cwd. Предыдущие каталоги попыток не удаляются. Для программного `runSwarm` используется опция `workspaceRoot`; при отсутствии опции длинный Windows cwd автоматически заменяется на `<project>/.pixso-artifacts/workspaces`. Если даже этот путь слишком длинный, выберите короткий `artifactsDir`, например `C:/pixso-artifacts`.

Неизменные успешные задания пропускаются при resume только после проверки fingerprint и SHA-256 каждого выходного файла. Fingerprint включает prompt, входные файлы, заданный coordinator контекст, команду, аргументы и явное окружение. Изменённый входной файл, изменённый/удалённый output или другое задание запускают новую попытку. Смена модели в унаследованных настройках GigaCode автоматически не определяется: для нового эксперимента используйте новый run.

Ненулевой exit, timeout, пустой output или отсутствие обязательного файла означают провал. Повторы ограничены `retries`; каждый пишет в новый каталог, поэтому остаток неудачной попытки не считается готовым результатом. При timeout завершается дерево процесса: `taskkill /T /F` с невидимым окном на Windows и группа процесса на Unix. Локальный lock не допускает два coordinator для одного run.

Worker не изменяет общий проект: пишет предложенные файлы в свой output. Coordinator проверяет схему, полное покрытие node IDs, допустимые пути и только затем переносит результат. Разделение cwd — защита от гонок, **не OS sandbox**. GigaCode имеет те же права, что и запускающий пользователь, и должен соблюдать указанную область записи. Используйте организационную изоляцию процессов, если требуется технически запретить доступ к другим файлам.

Успех subprocess означает лишь получение ожидаемых файлов. Финальная готовность требует полного источника данных, интеграции в проект, TypeScript/build, проверки DOM и сравнения локального Playwright снимка с независимым экспортом Pixso. Проверка не требует открыть корпоративный Pixso в браузере Playwright. Если эталон/шрифты/браузер недоступны, отчёт остаётся непроверенным, а не обещает совпадение.

С версии 1.1 анализ обязан дать `componentDecisions` для каждого узла. Координатор проверяет источники, экспорты, хеши и полное покрытие; затем сохраняет `component-plan.json` и `component-gaps.md`. Статус `blocked-design-system` означает, что реализация/apply не начались: GigaCode должен сообщить пользователю недостающие компоненты, требуемые адаптации и задание для ИИ из отчёта. После исправления библиотеки нужен новый анализ. `pixso_job_status` возвращает пути этого отчёта и причину остановки.

С версии 1.2 анализ также обязан дать `dataBindings` для каждого узла. Обычные подписи могут быть статическими; примерные бизнес-значения из дизайна связываются с существующими props/hooks/context и мок-сценариями проекта. Читаются реальные MSW/Mirage/json-server/Storybook/fixtures/factories либо собственные механизмы; `generation.data.mockFiles` задаёт явную инвентаризацию, `instructions` — правила использования, `setupFile` — существующий bootstrap только для анализа. Runtime не добавляет новую библиотеку данных.

`validation.setupFile` отдельно запускает preview: экспорт `preparePixsoPreview({screenId})` возвращает `{props?, Provider?}` после подготовки штатных моков. Этот модуль может явно вызвать bootstrap проекта. Mock/setup не импортируется в рабочую View, а дополнительный `validation.url` не заменяет настройку обязательного preview. Несуществующие сценарии, отсутствующий API/setup и неизвестная классификация дают `blocked-project-data` до генерации/apply. Покажите пользователю `data-gaps.md` с ID, причиной, точными доработками и заданием для ИИ; после исправления нужен новый анализ. [Контракт и примеры](project-data.md).

Финальная приёмка требует `pixelPerfect: true` для всех экранов: точное совпадение RGBA, без исключения сглаживания, обязательный preview установленных файлов, стабильность, шрифты, DOM и проверки проекта. `validation.url` добавляет проверку маршрутов, но не заменяет встроенный preview. Режим `tolerant` всегда диагностический и не завершает перенос. Подробности: `docs/pixel-perfect.md` в поставке.

## Optional skill и агенты

Для CLI без установки extensions можно скопировать `skills/pixso-react/` в `.gigacode/skills/pixso-react/`, а файлы `agents/*.md` — в `.gigacode/agents/`, сохраняя существующие конфигурации. Затем перезапустить GigaCode. Эти инструкции дополняют локальный MCP; они не устанавливают Node runtime, браузер и корпоративный GigaCode.

`pixso-screen-worker` отвечает за один экран/виджет. `pixso-design-reviewer` читает артефакты и проверяет доказательства. Основной исполняемый рой создаёт coordinator runtime; наличие именованных агентов само по себе не гарантирует параллельный запуск.
