# Моки проекта и данные из макета

Перенос должен сохранить разделение проекта между отображением и данными. Надпись «Сохранить» может остаться статической. Имя клиента, сумма заказа, дата, статус записи и повторяющиеся строки — примерные бизнес-данные: они должны поступать через настоящие props, hooks или context. Копирование таких значений непосредственно в JSX не является подключением данных.

## Конфигурация

Секция `generation.data` необязательна. При отсутствии явного списка runtime ищет существующие mocks/fixtures/factories/stories/handlers/seeds и признаки MSW, Mirage, json-server, Storybook либо собственного решения проекта. Поиск ограничен 200 файлами данных и 10 000 просмотренными записями каталога; неполный поиск отражается в профиле и блокирует согласование данных. Для большого проекта задайте полный явный список нужных файлов.

```json
{
  "generation": {
    "data": {
      "mockFiles": ["src/mocks/scenarios/orders.ts", "src/mocks/handlers.ts"],
      "instructions": "Использовать существующий сценарий заказа и штатный useOrder. Суммы и даты хранить в сценарии."
    }
  },
  "validation": {
    "setupFile": "src/preview/pixso-setup.tsx"
  }
}
```

Это фрагмент: сохраните остальные поля созданного `init` конфига. Все пути относительны к `projectRoot` и должны вести к реальным файлам проекта. [Полный пример](../examples/project-data.config.json) содержит условные ID и пути — замените их на свои. Пустой `mockFiles` включает обнаружение, а не отключает проверки. `generation.data.instructions` описывает правила уже существующего механизма, но не заменяет исходники и доказательства.

`generation.data.setupFile` — необязательный путь к уже существующему bootstrap моков. Runtime включает его в инвентаризацию и проверяет хеш, но не исполняет автоматически. `validation.setupFile` — отдельная точка запуска встроенного preview с контрактом ниже; при необходимости она явно импортирует и вызывает штатный bootstrap. Только `validation.setupFile` подготавливает установленный экран к проверке. Отдельный `validation.url` проверяет интеграцию дополнительно и не заменяет эту подготовку.

## Контракт preview

Setup — модуль целевого проекта, доступный браузеру. Он экспортирует именованную функцию:

```tsx
export async function preparePixsoPreview(
  { screenId }: { screenId: string }
) {
  // Эти функции и компоненты обозначают реальные API вашего проекта.
  const scenario = getExistingScenario(screenId);
  await startExistingMocks(scenario);
  return {
    props: scenario.viewProps,
    Provider: ExistingProjectProviders,
  };
}
```

Имена `getExistingScenario`, `startExistingMocks` и `ExistingProjectProviders` в примере условны: импортируйте соответствующие API из вашего проекта. `props` — объект входных свойств установленного `View`. `Provider` — необязательный React-компонент, принимающий `children`; он может подключить уже существующие theme/router/store/query-провайдеры. При сценарии только через props достаточно вернуть `{props}`; при чтении данных через hooks может понадобиться запуск штатных обработчиков и Provider. Возвращайте данные после завершения подготовки, чтобы первый кадр был проверяемым.

Используйте один воспроизводимый сценарий для конкретного `screenId`. Даты, случайные значения и сетевые ответы должны быть стабилизированы существующими средствами проекта. Если нужного ID/сценария нет, выдавайте явную ошибку. Полный backend, роутинг и новые состояния из картинки не выводятся.

Модули сценариев, обработчики и setup подключаются в preview, а не импортируются в production `View`. Компонент читает согласованные входные props или штатный data hook/context. Выбор новой mock-библиотеки и создание её инфраструктуры не выполняются скрыто.

## Обязательная проверка данных

Анализ записывает `dataBindings` для каждого назначенного узла: `none`, `static`, `dynamic` или `unknown`, причину и необходимые изменения. Для `dynamic` обязательны реальное выражение props/hook/context, источник API и существующая фикстура: пути, SHA-256 и точные выдержки. Значения для визуального сценария должны совпадать с захваченным дизайном.

Результаты сохраняются в `data-plan.json` и `data-gaps.md`. Неизвестная схема, отсутствующие моки или адаптер, неготовая настройка preview и неполная инвентаризация дают `blocked-project-data` до генерации и apply. Отчёт указывает экран/node ID, причину, необходимую доработку и готовое задание для ИИ. Добавьте нужный сценарий штатным способом, затем повторите анализ и `transfer`.

После генерации проверяются согласованные выражения и заявленные динамические текстовые значения; подстановка литерала и импорт mock/setup в рабочую View отклоняются. Хеши источников данных привязывают решение к проверенной версии проекта. Смысловое различение статического текста и бизнес-данных остаётся выводом ИИ. Автоматическая AST-проверка не доказывает произвольную семантику JavaScript; динамические нетекстовые поля без поддержанного адаптера остаются блокирующим пробелом. Затем всё равно обязательны TypeScript, DOM и точный PNG diff каждого выбранного экрана.

Корпоративные Pixso и GigaCode здесь недоступны. Тестовые процессы и локальный браузер проверяют механизм работы, но не подтверждают подключение ваших настоящих API и моков без запуска в целевом проекте.
