# Что подтверждает pixel perfect

MCP даёт модели доступ к дизайну и инструментам. Он не гарантирует, что модель правильно выберет компоненты или напишет точный CSS. Этот runtime проверяет результат и запрещает объявлять непрошедший перенос завершённым.

## Обязательная приёмка

1. Полная версия выбранной области дизайна со всеми узлами, ссылками и независимыми PNG. Для partial screen/microfrontend в покрытие входят выбранные корни и потомки, а предки сохраняются только как контекст. Каждый выбранный корень требует своего PNG, а не обрезки хост-снимка. SHA-256 PNG включён в канонический `captureHash`; изменение эталона вместе с его записью в манифесте не сохраняет идентичность версии.
2. Полный план компонентов. Для каждого узла — явное решение, для `reuse` — реальные файлы, SHA-256, существующий экспорт и фрагмент API. `adapt`, `create`, `unknown`, неопределённые выводы и неполный поиск блокируют перенос.
3. Полный план данных проекта. Для бизнес-значений подтверждаются реальные источники props/hooks/context и существующие фикстуры; отсутствующие сценарии, неизвестные привязки и неподготовленный preview блокируют перенос. Рабочие View не импортируют моки и не подменяют заявленные динамические значения литералами.
4. Компиляция установленного кода и команды проекта. Файлы компонентов, CSS, данных, preview setup, входы TypeScript и реально загруженные preview-зависимости проверяются на изменение в процессе приёмки.
5. Запуск именно установленных экранов во встроенном Vite preview. `validation.setupFile` экспортирует асинхронный `preparePixsoPreview({screenId})`, возвращающий `{props?, Provider?}`. Указанный `validation.url` проверяется дополнительно и не может подтвердить другой, ошибочный код или заменить подготовку данных.
6. Проверка каждого экрана в исходном viewport при deviceScaleFactor=1, без изменения размеров эталона. Ожидаются загрузка изображений/шрифтов, два стабильных снимка, точные ID, тексты, геометрия, стили и видимость.
7. Побайтовое сравнение декодированных RGBA-пикселей. `pixelDiffPixels` должен быть **0**. Нет порога различия цвета и исключения сглаженных краёв. Изменение одного канала одного пикселя на 1 блокирует результат.

Только успешное выполнение всех пунктов даёт общие `pixelPerfect: true`, `complete: true`, `status: "accepted"`. Допуск DOM 0.01 px учитывает округление координат браузера; он не ослабляет растровое сравнение. Даже явно заданный `maxPixelDiffRatio: 1` не ослабляет строгий режим.

Отчёт содержит PNG результата и разницы, число отличающихся пикселей, максимальную разницу каналов, область расхождений, сведения о шрифтах, стабильности и настройках сравнения. `tolerant` сохраняет точные метрики рядом с перцептивной диагностикой и всегда остаётся `complete: false`.

## Когда дизайн-системы недостаточно

В конфигурации можно указать:

```json
{
  "generation": {
    "designSystem": { "name": "Corporate UI", "packageName": "@company/ui" },
    "componentFiles": ["src/ui/Button.tsx", "src/ui/TextField.tsx"],
    "cssFiles": ["src/styles/tokens.css", "src/ui/components.css"]
  }
}
```

Это фрагмент секции; остальные поля оставьте из `init`. Для библиотеки в исходниках без npm-пакета `packageName` не нужен. Полный список реальных файлов важнее имени системы.

Например, дизайн требует `Button` высотой 36 px, с leading icon и отдельным loading-состоянием, а библиотека предоставляет только высоты 32/40 и не имеет loading API. Анализ должен вернуть `adapt`, перечислить недостающие возможности и исходники. Если компонента нет — `create`. Использовать ближайший вариант и скрыть расхождение запрещено.

`component-gaps.md` содержит экран и node ID, требуемые свойства, доступные возможности, причины, конкретные изменения и готовое задание для ИИ. GigaCode обязан перечислить эти проблемы пользователю. До исправления библиотеки реализация и apply не запускаются. После доработки нужен новый анализ: старое решение привязано к хешам исходников. Анализ, в котором ИИ пропустил решения или выдумал экспорт, также блокируется.

## Границы доказательства

Точная проверка относится к сохранённым экранам, состояниям, viewport и браузеру/ОС проверки. Она не доказывает состояния, которых нет в дизайне, неизвестные брейкпоинты или поведение в другом браузере.

Pixso и браузер могут по-разному растрировать один шрифт. В строгом режиме это будет расхождением: runtime не подменяет точность увеличенным допуском. Нужно разобраться со шрифтами/окружением либо честно оставить результат непрошедшим.

Файлы, экспорты и покрытие плана компонентов проверяются механически, но смысловая совместимость API остаётся выводом ИИ. Именно поэтому она не заменяет проверку результата.

Различение статических подписей и бизнес-данных также остаётся явным выводом ИИ. Контроль `data-plan.json` подтверждает объявленные источники, хеши, фикстуры и поддержанные текстовые привязки, а не семантику любого приложения. Неподдержанные нетекстовые динамические поля требуют адаптера и блокируют перенос. [Настройка моков](project-data.md). Короткий `CHANGELOG.md` — необязательная сводка, не дополнительное доказательство точности.

Есть проверки против перекрытия UI скриншотом, прозрачных текстов и незаявленных raster/canvas-слоёв; прямое обслуживание артефактов дизайна из встроенного preview запрещено. Эти проверки ловят известные подмены, но не являются математическим доказательством семантики произвольного JavaScript/CSS. Проверка взаимодействий и доступности реального приложения остаётся частью проектных тестов.

Официальный API не предоставляет здесь доказанную атомарную транзакцию захвата. Проверки свойств до/после выявляют изменения, но не доказывают отсутствие временных изменений с последующим откатом. Во время экспорта дизайн должен оставаться стабильным. Происхождение вручную импортированного эталона предполагает доверие к исходному экспорту.

Реальный корпоративный Pixso/GigaCode не проверен без доступа. [Отчёт поставки](verification.md) отдельно перечисляет настоящий браузер, отрицательные тесты и имитацию CLI/API.
